Browsers block part of your page: the http-file fix

A family dental office moved its website to https years ago, and the padlock showed in the address bar, so everyone assumed the job was done. But the home page still pulled four files over plain http://: the web font, one stylesheet, the slider script and the online-booking widget. Browsers refuse to load scripts and stylesheets over http on an https page, and they do it silently - no warning bar, no error the owner would ever see. Visitors got a plain-font page, a slider stuck on its first photo, and an empty box where "Book online" should have been. Here is what was found, what changed, and how long it took.

Check yours in thirty seconds: open your home page in Chrome on a computer, press F12 (or right-click > Inspect) and click Console. A red line starting "Mixed Content: The page at 'https://...' was loaded over HTTPS, but requested an insecure ..." names each file the browser blocked. No such lines means your page is clean.

What was wrong

When a site switches to https, links typed into the page, the theme settings or the database years earlier keep their old http:// address. The page itself is secure, so the padlock shows, but each of those files is asked for over an unencrypted connection, and browsers block scripts, stylesheets and embedded frames fetched that way. Images are usually retried over https, and simply go missing if that fails.

Before (in the page source):
  <link rel="stylesheet" href="http://fonts.example.com/css?family=Lato">
  <script src="http://www.yourdomain.com/wp-content/themes/x/slider.js"></script>
  <iframe src="http://booking.example.com/widget?office=123"></iframe>

After:
  <link rel="stylesheet" href="https://fonts.example.com/css?family=Lato">
  <script src="https://www.yourdomain.com/wp-content/themes/x/slider.js"></script>
  <iframe src="https://booking.example.com/widget?office=123"></iframe>

How it was fixed

  1. List every blocked file from the Console on the home page and the other main pages (contact, booking, services).
  2. Files on your own domain: change http://yourdomain.com to https://yourdomain.com wherever it is stored. On WordPress that is one database search-and-replace (the free Better Search Replace plugin), run on a backup first; on Wix, Squarespace or Shopify it is the section or embed setting that holds the address.
  3. Files from other companies (fonts, widgets, booking or chat tools): switch the address to https, or re-copy the provider's current embed code, which is https today.
  4. Re-check the Console on each page in a private window, so nothing comes from the cache.
