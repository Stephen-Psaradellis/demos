"Cannot modify header information - headers already sent" in WordPress

The page shows a warning like "Cannot modify header information - headers already sent by (output started at /wp-content/themes/yours/functions.php:42)", and often the login or a redirect stops working with it. Before WordPress can send a redirect or a login cookie, nothing may have been printed to the page. Some file printed something first: usually a blank line, a space or an invisible byte-order mark before <?php or after a closing ?>. The message tells you exactly where: the part in brackets after "output started at" is the file and line to fix, not the file the warning is "in".

What the owner sees

harborbakery.example/wp-login.php

What the checks found


  





Find out which case it is (five minutes)


    
  
  1. Read the brackets. Copy the path after "output started at". That file and line number printed too early. The file named before it (often pluggable.php or wp-login.php) is only where WordPress noticed, and is almost never the one to change.
    2. 
  
  2. Did you just edit a file? A recent edit to functions.php or wp-config.php, or a snippet pasted from a website, is the usual source. A space or empty line before the first <?php, or after a final ?>, is enough.
    3. 
  
  3. Does it name a plugin folder? A path under wp-content/plugins/ means that plugin printed something early, often right after an update. Its name is the folder after plugins/.
    4. 
  
  4. Is the line a warning itself? If the line shown printed a PHP notice or deprecation message (see PHP warnings on the site), that printed text is what broke the headers. Fix or hide the first warning and this one goes with it.
    5. 




The fixes, by case


    
  
  1. Take a copy of the file first (download it with the host's File Manager or FTP). You are about to remove a few characters, and a copy makes that reversible.
    2. 
  
  2. Stray space or blank line: open the file named in the brackets in the host's File Manager editor, go to the very top, and make sure <?php is the first thing in the file, with nothing before it. At the very end, delete a closing ?> and any blank lines after it; WordPress files do not need one.
    3. 
  
  3. Invisible byte-order mark: if the top looks clean, the file was saved with a "BOM" by a desktop editor. Re-save it as "UTF-8 without BOM" (Notepad++: Encoding, UTF-8; VS Code: click "UTF-8 with BOM" in the status bar, Save with Encoding, UTF-8) and upload it again.
    4. 
  
  4. A plugin is printing early: rename its folder in wp-content/plugins/ (add -off), check the site works, then update or replace that plugin before turning it back on.
    5. 
  
  5. A PHP warning is printing: on a live site, warnings should go to a log, not the page. In wp-config.php set define('WP_DEBUG_DISPLAY', false); and fix the warning itself when you can.
    6. 
  
  6. Log in and check again: clear the browser cache, log in, save a post. No warning at the top and a working redirect means it is fixed.
    7.

What not to do


    
  
  • Do not edit pluggable.php or wp-login.php. They are where WordPress noticed the problem, not the cause, and an update overwrites them anyway.
    • 
  
  • Do not wrap the site in ob_start() to hide the warning. It covers the real fault and makes the next one harder to find.
    • 
  
  • Do not edit a theme file with the built-in Theme File Editor if you cannot reach the host's file manager too: one wrong character can lock you out of the dashboard.
    • 
  
  • Do not install a "fix headers" plugin. The fix is a few characters in one named file.
    •
